# 性能の安定化と AR の見せ方：調査まとめ

作成日：2026-10-13（デモ版の実機テストの結果をふまえて）

## 0. 結論（先に要点）

- **iPhone のブラウザには、使えるメモリに端末の搭載メモリよりずっと低い上限があります**。超えるとエラーを出さずにページが読み直されます。デモで「最初の画面に戻される」のはこれです。上限の値は公開されていませんが、報告では 1.25GB 前後で強制終了された例があります。Canvas には別枠で合計 384MB の上限もあります（[WebKit Bug 219780](https://bugs.webkit.org/show_bug.cgi?id=219780)、[WebKit Bug 195325](https://bugs.webkit.org/show_bug.cgi?id=195325)）。
- 今のように**撮影・合成・人物検出・奥行き推定・3D 表示をすべて1つのページで行う作りでは、iPhone で「必ず落ちない」ようにするのは難しい**です。対策で落ちにくくはできますが、端末や iOS のバージョン次第で落ちる余地が残ります。確実にするには、①処理を段階ごとに分けて毎回ページを読み直すか、②重い処理をサーバーに移す必要があります。
- **iPhone の Safari は WebXR の AR（immersive-ar）に対応していません**（2026年10月時点。[WebXR on iOS](https://xrdoctors.pro/blog/webxr-on-ios-what-actually-works)、[Apple Developer Forums](https://developer.apple.com/forums/thread/756850)）。そのため、ブラウザの AR は「方位センサーで向きを合わせて画面に重ねる」方式が限界です。景色に貼り付いて動かない AR（6DoF の追跡）はできません。
- 方位センサー（コンパス）の誤差は、報告で ±10° 前後、悪いと 30° 程度です（[W3C geolocation ML](https://lists.w3.org/Archives/Public/public-geolocation/2011Jul/0014.html)、[ArcGIS compass sample](https://developers.arcgis.com/javascript/jssamples/mobile_compass.html)）。**AR の「パンチが弱い」主な原因は、このずれ・揺れと、撮った直後の同じ景色を重ねていて変化が見えないこと**だと考えています。
- 一方、ブラウザのままでも次の改善はできます。
  - センサーの組み合わせ方を変えて揺れを抑える
  - カメラ映像とパノラマを照合して、向きを自動で補正する
  - 見せ方を工夫する（時間・季節の違いを強調する演出）

---

## 1. 実機テストで分かったこと

| 症状 | 原因の見立て |
| --- | --- |
| 奥行き推定の直後・最中にページが読み直される | 人物検出（MediaPipe）と奥行き推定（ONNX Runtime）のメモリが同時に残っていた。Worker の終了・検出器の解放・Canvas の解放で改善した |
| 仕上がり確認画面で読み直される（今も時々） | ページを読み直した後でも起きるので、仕上がり確認画面そのものの GPU メモリ（3D 表示＋大きな画像）が上限に近いと考えられる |
| 投稿後に「Loading error.」 | IndexedDB の画像の保存方法による不具合。画像を複製して保存するよう修正済み |
| AR のパンチが弱い | 下の「3. AR」で分析 |

## 2. 性能を安定させる方法

効果が大きく、手間が小さい順に並べています。メモリ量は画像サイズからの見積もりです。

### 2-1. すぐできるもの（ブラウザのまま）

| # | 方法 | 見込める効果 | 影響・注意 |
| --- | --- | --- | --- |
| A | **3D 表示の描画設定を軽くする**：アンチエイリアス（MSAA）を切り、iPhone では描画解像度の倍率を 2 → 1.5 にする | 画面用の GPU メモリ。iPhone の画面（約 780×1690px 相当）で MSAA×4 だと約 40MB → 約 6MB | 斜めの線が少しギザギザになる。パノラマの写真ではほぼ目立たない |
| B | **AR 用テクスチャのミップマップを作らない** | 4096px の画像で約 8MB 減（24MB → 約 32MB になっていたのが 24MB に） | AR は画像を拡大して見るだけなので、見た目は変わらない |
| C | **人物検出を Worker に移す**（使い終わったら Worker を終了） | MediaPipe のメモリ（数十〜100MB 程度）を確実に解放できる | MediaPipe を module Worker で動かすには工夫が要る。動かなければ C' を使う |
| C' | **人物検出を縮小画像（2048px）で行い、見つけた枠を元の画像に当ててぼかす** | 検出中の 4096px の作業領域（約 50MB）が 1/4 に | 小さく写った人を見逃しやすくなる |
| D | **処理を段階ごとに分け、段階ごとに保存してページを読み直す**（合成 → 読み直し → 人物検出 → 読み直し → 奥行き推定 → 読み直し → 仕上がり確認） | 各段階の最大メモリが、その段階の分だけになる。今「仕上がり確認の前だけ」に入れている読み直しを全段階に広げる形 | 読み直しのたびに 1〜2 秒かかる。モデルの読み込みはブラウザのキャッシュから |
| E | **画面サイズや GPU に合わせて、描画の細かさを自動で下げる**（3D の分割数 512×128 → 256×64 など） | 頂点データが 1/4。描画も軽くなる | 奥行きの凹凸が少し粗くなる |

### 2-2. 測り方（推測ではなく数字で判断するために）

- **Mac をお持ちの場合**：iPhone を Mac につないで Safari の Web インスペクタを開き、「タイムライン」の「メモリ」で、どの段階でどれだけ増えるかを記録できます。iPhone のメモリ上限は PC の Safari では再現しません（[WebKit Bug 219780](https://bugs.webkit.org/show_bug.cgi?id=219780)）。
- **Mac がない場合**：アプリ側で「今どの大きな画像・モデルを持っているか」の見積もりをデバッグパネルに出せます。正確な値ではありませんが、段階ごとの比較には使えます。

### 2-3. 根本的な方法（本番に向けて）

| 方法 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **サーバーで処理する** | スマホは撮影と送信だけを行う。合成・人物検出・奥行き推定は GPU サーバーで行い、結果を Cloudinary に置く | iPhone のメモリ上限から完全に解放される。処理も速く、結果が端末によらずそろう | サーバー費用がかかる。デモ版の「バックエンドなし」の方針から外れる |
| **ネイティブアプリにする** | ARKit / ARCore を直接使う | メモリの余裕が大きい。AR の追跡も本物になる（3章） | 開発コストが大きい。Web から外れる |

> **限界として書いておくべきこと**：ブラウザだけで iPhone を対象にする限り、メモリ上限は Apple が決めていて、アプリ側から増やせません。2-1 の対策で「落ちにくく」はできますが、「どの iPhone でも必ず落ちない」とは言い切れません。本番で安定性を最優先するなら、2-3 のサーバー処理が最も確実です。

## 3. AR の見せ方を強くする方法

### 3-1. なぜ「パンチが弱い」か（今の実装の分析）

1. **ずれと揺れ**：向きを方位センサー（コンパス）だけで決めているため、±10° 前後ずれたり細かく揺れたりします。重ねた画像が景色に「貼り付いて」見えないので、合成っぽく見えます。
2. **景色に固定されていない**：iPhone のブラウザでは AR の追跡（WebXR）が使えません。画像は画面に描いているだけで、スマホを平行移動しても景色との位置関係は変わりません。
3. **重ねる内容に差がない**：テストでは撮った直後のパノラマを重ねたため、重ねても今の景色とほとんど同じで、変化が見えません。本来の価値は「別の季節・別の時間の景色」を重ねることです。
4. **重ね方が控えめ**：既定の不透明度 0.8 で全体を薄く重ねていて、奥行きによる切り抜きの境目もぼかしています。

### 3-2. ブラウザのままできる改善

| # | 方法 | 何が良くなるか | 手間 |
| --- | --- | --- | --- |
| F | **ジャイロとコンパスを組み合わせる**：細かい動きは反応の速いジャイロ（回転速度）で追い、ゆっくりとしたずれだけコンパスで直す。一般に「相補フィルタ」と呼ばれる方法 | 揺れが大きく減り、スマホを振っても遅れずについてくる。「貼り付いた」感じに近づく | 小 |
| G | **カメラ映像とパノラマを照合して向きを自動補正する**：映像とパノラマを小さく縮めて、空と建物の境目（スカイライン）の形を左右にずらしながら比べ、一番合う位置をずれとして使う | コンパスの ±10° のずれが自動で消える。本番で予定している自動補正（heading_correction）の試作にもなる | 中 |
| H | **見せ方の演出** | 差がはっきり見える。体験として印象に残る | 小〜中 |
|  | ・指でなぞった部分だけ過去の景色が見える「のぞき窓」 | | |
|  | ・時間スライダーで今と過去を行き来する | | |
|  | ・切り替え時に波紋やフェードを入れる | | |
|  | ・季節・時間帯が違うパノラマを優先して重ねる（今あるまとめ表示を使う） | | |
| I | **空だけを入れ替える**：カメラ映像から空の部分を検出し、そこに過去のパノラマの空（夕焼け・雪空など）を入れる | 時間・季節の違いが一目で分かる | 中〜大。MediaPipe 標準の分割モデル（DeepLab v3）には「空」の分類がない見込みなので、空を学習したモデルを探して変換する必要がある（[MediaPipe Image Segmenter](https://developers.google.com/edge/mediapipe/solutions/vision/image_segmenter/web_js)）。簡易版として、画面上部の色と明るさから空を推定する方法もある |

### 3-3. ブラウザの限界と、その先

| 端末 | ブラウザでできること | できないこと |
| --- | --- | --- |
| **iPhone（Safari）** | 方位センサーで向きを合わせて重ねる（今の方式）＋F・G・H・I | 景色に固定する AR（WebXR が未対応）。AR Quick Look は 3D モデルを置く用途で、パノラマを景色に重ねる用途には向かない |
| **Android（Chrome）** | WebXR の AR が使える。位置の追跡、平面への当たり判定、奥行き（Depth API）、光の推定が使える（[ARCore と WebXR の比較](https://developers.google.com/ar/develop/webxr/arcore-comparison?hl=en)） | ― |

- iPhone で景色に固定する AR を Web で実現していた代表的なサービスの 8th Wall は、2026年2月で新規開発を終了しています。公開済みの体験も 2027年2月まで、その後はエンジンの一部がオープンソース化された形での自前運用になります（[8th Wall フォーラム](https://forum.8thwall.com/t/important-changes-to-8th-wall-business/8578)）。卒業制作で新たに採用するのはおすすめしません。
- **iPhone で一番強い AR が必要なら、ネイティブアプリ（ARKit）が必要**です。

> **限界として書いておくべきこと**：iPhone のブラウザでは、AR の土台が「コンパス＋傾きセンサー」です。そのため、ネイティブの AR アプリのような「景色に貼り付いて動かない」重ね方はできません。F（揺れの抑制）と G（画像による向きの補正）でかなり近づけられますが、近くの物（数メートル以内）の位置は合いません。遠景（建物・山・空）を重ねる今の設計は、この制約の中では理にかなっています。

## 4. おすすめの進め方

1. **安定化**：A（描画設定）、B（ミップマップ省略）、C または C'（人物検出のメモリ）。どれも見た目への影響が小さく、すぐ入れられます。まだ落ちる場合は D（段階ごとの読み直し）。
2. **AR の強化**：F（揺れの抑制）→ G（向きの自動補正）→ H（見せ方の演出）の順。F と G で「ずれて見える」を減らしてから、H で「差を見せる」と効果が出やすいです。
3. **発表・評価の工夫**：AR は「同じ場所で、別の季節・時間に撮ったパノラマ」を重ねて見せると価値が伝わります（テストでは撮影直後の同じ景色だったため、差が見えませんでした）。
4. **本番の方針**：iPhone の安定性と AR の質を最優先するなら、「サーバーでの処理（2-3）」と「ネイティブ AR（3-3）」を検討する価値があります。
