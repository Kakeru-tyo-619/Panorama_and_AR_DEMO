# 人物合成モード シーケンス図

作成日：2026-10-15（同日更新：パノラマと AR の 2 段階生成に変更）
関連資料：[人物合成モード 実装方針](person_composite_mode.md)

## 役割分担

- **AI のモデルを動かす処理**：投稿時の CPU サーバー
  - ① パノラマ（すぐ）：合成・人物の切り抜き・人物の除去
  - ② AR（後から）：奥行き推定・空マスク
- **シェーダーでできる仕上げ**：閲覧時の WebGL（1回だけ）
- **毎フレーム必要な処理**：スマホでの人物の切り抜き・距離の推定・合成

## 生成の方針

- パノラマを先に作って投稿者に返し、AR は後から作る。
- 投稿時に「AR は数分ほどで使えるようになります」と表示し、**AR の完成は通知しない**。
- AR の状態は、パノラマの画面で表示する（準備中／利用できる／利用できない）。
- AR の生成に失敗しても、パノラマは 360度ビュー（平面）で見られる。撮り直しは不要。
- **人が写ったまま公開しないよう、人物の除去はパノラマの段階で必ず行う。**

### AR の状態（`panoramas.ar_status`）

| 値 | 意味 | 画面の表示 |
| --- | --- | --- |
| `pending` | 生成中 | 「AR は数分ほどで使えるようになります」。AR ボタンは押せない |
| `ready` | 生成済み | AR ボタンを有効にする。`depth_map_url` などが入っている |
| `failed` | 生成に失敗 | 360度ビュー（平面）だけで表示する。`depth_map_url` は空 |

## 1. 投稿時

スマホは画像を直接 Cloudinary に送り、Workers は受付・登録・依頼だけを担当する。CPU サーバーは ① パノラマを作って知らせたあと、続けて ② AR を作る。

```mermaid
sequenceDiagram
    participant S as スマホ
    participant W as Workers（Hono）
    participant D as D1
    participant C as Cloudinary
    participant P as CPUサーバー

    S->>W: 投稿開始
    W->>D: 処理中で登録（非公開）
    W-->>S: アップロード署名
    S->>C: 元画像12枚＋撮影記録
    S->>W: 送信完了
    W->>P: 処理を依頼（投稿ID）
    W-->>S: 受付（処理中）

    rect rgba(128, 128, 128, 0.1)
    Note over P: ① パノラマ（すぐ）
    P->>C: 元画像を取得
    Note over P: 合成（OpenCV）<br/>人物・空の切り抜き（SkyWater-Seg）<br/>人物の除去（LaMa）<br/>閲覧用の低解像度版を作成
    P->>C: パノラマを保存
    P->>C: 元画像を削除

    alt パノラマの作成に成功
        P->>W: パノラマ完成を通知
        W->>D: パノラマ完成・AR は pending に更新
    else パノラマの作成に失敗
        P->>W: 失敗を通知
        W->>D: 失敗に更新
    end
    end

    loop パノラマ完成または失敗まで
        S->>W: 状態を確認
        W->>D: 状態を取得
        W-->>S: 処理中／パノラマ完成／失敗
    end

    Note over S: 仕上がり確認の画面<br/>「AR は数分ほどで使えるようになります」
    S->>W: 公開
    W->>D: 公開に更新（1日1件の確認を含めてトランザクションで）
    W-->>S: 公開完了

    rect rgba(128, 128, 128, 0.1)
    Note over P: ② AR（後から。通知はしない）
    Note over P: 奥行き推定（人物除去後のパノラマ・縮小解像度）<br/>空マスク（①の切り抜き結果を使う）<br/>AR 用の書き出し
    P->>C: 奥行きマップ・空マスクを保存

    alt AR の作成に成功
        P->>W: AR 完成を通知
        W->>D: ar_status を ready に、depth_map_url を登録
    else AR の作成に失敗
        P->>W: AR 失敗を通知
        W->>D: ar_status を failed に更新
    end
    end
```

## 2. 閲覧時

サーバーの処理は入らない。スマホが保存済みのデータを受け取り、AR の状態に応じて表示を切り替える。

```mermaid
sequenceDiagram
    participant S as スマホ（WebGL）
    participant W as Workers（Hono）
    participant D as D1
    participant C as Cloudinary

    S->>W: パノラマを要求
    W->>D: 撮影情報・ar_status を検索
    W-->>S: 画像URL・撮影情報・ar_status

    S->>C: パノラマ（閲覧用）を取得
    C-->>S: データ

    alt ar_status が ready
        S->>C: 高解像度版・奥行き・マスクを取得
        C-->>S: データ
        Note over S: 準備（1回だけ）<br/>奥行きを拡大（境目の補正）<br/>空の奥行きを無限遠に<br/>奥行きの段差でメッシュを切る
        Note over S: AR ボタンを有効にする

        loop AR 表示中、毎フレーム
            Note over S: カメラ映像を取得<br/>人物を切り抜き（15〜30回/秒）<br/>足元・身長から距離を推定<br/>パノラマと合成
        end
    else ar_status が pending
        Note over S: 360度ビュー（平面）で表示<br/>「AR は数分ほどで使えるようになります」
    else ar_status が failed
        Note over S: 360度ビュー（平面）だけで表示
    end
```

## 補足

- 投稿時の「状態を確認」は、一定間隔で問い合わせる方式を想定している。待つのはパノラマの完成までで、AR の完成は待たない。
- ① パノラマの処理時間は実測して、「すぐ」と言える範囲（例：1分以内）に収まるか確認する。収まらない場合は、①では顔ぼかしだけにして、②で人物除去版に差し替える。
- 「数分ほど」の目安は、実測した ② の処理時間に余裕を足して決める。処理が重なると待ち時間が延びるので、幅を持たせた書き方にする。
- 人が写った元画像は、① のパノラマを保存した直後に Cloudinary から削除する（② は人物除去後のパノラマを使うので、元画像は不要）。
- CPU サーバーの処理は、同じ投稿を2回処理しても結果が壊れないように作る（保存先を投稿 ID で固定する）。
- 1日1件の数え方は、公開した時点で数える案にしている。失敗した投稿は数えないので、その日のうちに撮り直せる。
- 投稿者が AR の出来を確認しないまま公開されるため、投稿者がマイページで AR の状態と見た目を確認できるようにするか、閲覧者が「表示がおかしい」と報告できるようにすることを検討する。
- D1 では `panoramas` に `ar_status` を追加し、AR が完成するまで `depth_map_url` を空にしておく。
